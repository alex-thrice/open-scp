# План разработки кроссплатформенного файлового клиента

## 1. Назначение документа

Этот документ является исполняемым планом разработки настольного приложения — кроссплатформенного аналога WinSCP с обязательной поддержкой:

- локальной файловой системы;
- SFTP;
- S3-совместимых хранилищ;
- macOS на Apple Silicon как основной платформы;
- Windows и Linux как поддерживаемых платформ;
- локализации интерфейса, начиная с русского и английского языков.

План разбит на небольшие задачи с зависимостями и критериями готовности. Агенту следует поручать одну задачу по её идентификатору, например: `Выполни задачу T03 из IMPLEMENTATION_PLAN.md`.

## 2. Зафиксированные решения

| Область | Решение |
|---|---|
| Desktop runtime | Electron |
| Язык | TypeScript со строгими настройками |
| UI | React + Vite |
| SFTP | `ssh2` напрямую через собственный адаптер |
| S3 | AWS SDK for JavaScript v3 |
| Хранение метаданных | SQLite с версионируемыми миграциями |
| Хранение секретов | Electron `safeStorage`; незашифрованное хранение запрещено |
| Локализация | `i18next` с ключами, не зависящими от текста |
| Валидация IPC и данных | Zod |
| Unit/integration tests | Vitest |
| UI end-to-end tests | Playwright |
| Основной интерфейс | Двухпанельный Commander: локальная панель слева, удалённая справа |

Версии Node.js, Electron и зависимостей фиксируются в lock-файле при выполнении T01. Следует использовать актуальную поддерживаемую LTS-версию Node.js и стабильную версию Electron на момент создания проекта, не использовать `latest` без фиксации версии.

## 3. Границы первой версии

### 3.1. Обязательно для MVP

- создание и редактирование профилей SFTP и S3;
- безопасное хранение секретов;
- проверка host key для SFTP;
- подключение и повторное подключение;
- навигация по локальной и удалённой файловой системе;
- сортировка и виртуализация больших списков;
- upload и download файлов и каталогов;
- очередь, прогресс, отмена и повтор операций;
- создание каталогов;
- переименование, перемещение и удаление;
- обработка конфликтов имён;
- частичное продолжение передачи там, где это безопасно;
- русский и английский интерфейс;
- сборка для macOS arm64;
- автоматические тесты против OpenSSH и MinIO;
- базовые сборки для Windows x64 и Linux x64.

### 3.2. Не входит в MVP

- FTP/FTPS, SCP, WebDAV и облачные провайдеры кроме S3;
- удалённый терминал;
- встроенный текстовый редактор;
- полноценная синхронизация каталогов;
- сравнение каталогов по содержимому;
- SFTP jump hosts и сложные proxy-сценарии;
- изменение владельца файлов;
- работа с S3 Object Lock и полное управление версиями объектов;
- монтаж удалённого хранилища как системного диска;
- плагины сторонних разработчиков.

Эти возможности нельзя добавлять «заодно» при выполнении задач MVP. Для них создаются отдельные задачи после завершения M5.

## 4. Правила работы агента

Перед выполнением каждой задачи агент обязан:

1. Прочитать `AGENTS.md` и этот документ целиком.
2. Проверить состояние рабочего дерева и не изменять посторонние пользовательские изменения.
3. Выполнять только одну указанную задачу и её необходимые зависимости.
4. Не копировать исходный код, графику, переводы и другие материалы из `winscp-master`.
5. Использовать WinSCP только как источник информации о поведении и пользовательских сценариях, пока отдельно не принято лицензионное решение.
6. Не помещать AWS SDK, `ssh2`, Node.js API, SQLite или секреты в renderer process.
7. Добавлять или обновлять тесты вместе с реализацией.
8. Выполнить относящиеся к задаче проверки и привести их результаты в отчёте.
9. Обновить статус задачи в этом файле только после выполнения всех критериев готовности.
10. Не создавать commit, branch или pull request, если это явно не включено в поручение.

Если задача обнаруживает необходимость изменить архитектурное решение, агент должен остановиться, описать проблему и предложить ADR. Нельзя молча менять публичные контракты провайдеров, модель IPC или формат базы данных.

## 5. Общая Definition of Done

Задача считается выполненной, когда:

- реализованы все пункты её объёма работ;
- выполнены её критерии приёмки;
- TypeScript компилируется без ошибок и без необоснованных `any`;
- линтер и относящиеся к изменению тесты проходят;
- новые ошибки имеют типизированный код и понятное пользователю локализуемое сообщение;
- секреты и чувствительные данные отсутствуют в логах, fixtures и snapshot-файлах;
- документация соответствует фактическому поведению;
- задача отмечена `[x]`, а под ней добавлен краткий блок `Результат` с командами проверки.

Начиная с T02, стандартные проверки должны запускаться командами:

```bash
pnpm lint
pnpm typecheck
pnpm test
```

После появления соответствующей инфраструктуры также используются:

```bash
pnpm test:integration
pnpm test:e2e
pnpm package
```

## 6. Целевая архитектура

```text
Renderer process
└── React UI
    ├── Commander panels
    ├── Connection manager
    ├── Transfer queue
    └── Dialogs and notifications
             │
             │ Typed, validated IPC
             ▼
Preload process
└── Minimal contextBridge API
             │
             ▼
Main process
├── Session manager
├── Connection profile service
├── Credential service
├── Transfer engine
├── Operation queue
├── Persistence and migrations
└── File system providers
    ├── LocalProvider
    ├── SftpProvider
    └── S3Provider
             │
             ▼
OS filesystem / OpenSSH servers / S3-compatible storage
```

### 6.1. Правила процессов Electron

- `nodeIntegration: false`;
- `contextIsolation: true`;
- renderer sandbox включён;
- renderer не импортирует Node.js и Electron API;
- preload экспортирует только узкий типизированный API;
- входные и выходные данные IPC валидируются;
- запрещены произвольные имена IPC-каналов, переданные renderer-процессом;
- навигация на внешние страницы и создание окон запрещены по умолчанию;
- Content Security Policy не допускает `unsafe-eval` в production;
- пути файлов, credentials и содержимое ключей не отправляются в renderer без необходимости.

### 6.3. Базовые доменные контракты

Провайдеры не должны сводиться к ложному «наименьшему общему знаменателю». Общий интерфейс сопровождается явными возможностями протокола.

Минимальные сущности:

- `ConnectionProfile` — discriminated union для SFTP и S3 без секретов;
- `SecretReference` — ссылка на секрет в защищённом хранилище;
- `FileSystemEntry` — файл, каталог, симлинк или специальный объект;
- `ProviderPath` — путь с указанием типа провайдера и без предположения о POSIX-семантике;
- `ProviderCapabilities` — поддерживаемые операции и особенности;
- `FileSystemProvider` — подключение, list/stat, создание, удаление, rename и потоковый I/O;
- `TransferOperation` — источник, назначение, политика конфликта и состояние;
- `ApplicationError` — типизированная ошибка с машинным кодом и безопасными параметрами локализации.

Примеры capabilities:

- настоящие каталоги;
- права доступа;
- симлинки;
- атомарный rename;
- server-side copy;
- multipart upload;
- продолжение upload/download;
- контроль времени изменения;
- checksum.

#### [x] T05. Реализовать LocalProvider

**Цель:** дать UI и Transfer Engine реального локального поставщика файловой системы.

**Работы:**

**Результат:**

  отмены, Windows junction/symlink и защиты внешнего target;

  `pnpm build` и `pnpm package`; 28 тестов пройдены, packaged-приложение прошло smoke-запуск.

- существующий объект не изменяется до явного решения пользователя;
- выбор «для всех» действует только в пределах соответствующей операции;
- после перезапуска ожидающий конфликт остаётся безопасно приостановленным.

**Результат:**

- копирование сразу ставится в очередь с политикой `ask`; запрос появляется только после
  фактического обнаружения существующего назначения и не останавливает другие задания;
- диалог показывает источник и назначение, поддерживает overwrite/skip/rename/cancel для одного
  конфликта или всех оставшихся конфликтов только текущего задания;
- ожидающий конфликт сохраняется в журнале без автоматической перезаписи, а повторная проверка
  перед публикацией обрабатывает появление назначения во время копирования;
- проверки: `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:integration`, `pnpm test:e2e`,
  `pnpm package:win`, `pnpm test:packaged`.

#### [x] T25. Открывать локальный файл двойным щелчком в приложении по умолчанию

- ошибки внешнего приложения локализованы и проходят через общий безопасный IPC-контракт;

### M7. Состояние и восстановление подключений

#### [x] T27. Восстанавливать последние локальные и удалённые пути

**Зависимости:** T16.

**Цель:** возвращать пользователя к последнему успешно открытому каталогу.

**Работы:**

- хранить последний успешный путь отдельно для каждого локального диска/корня;
- хранить последний успешный удалённый путь по стабильному идентификатору профиля;
- при запуске приложения восстанавливать доступные локальные пути панелей;
- при повторном подключении к тому же SFTP-профилю открывать его последний путь;
- обновлять запись только после успешного листинга каталога;
- при удалённом, переименованном или недоступном каталоге переходить к ближайшему доступному
  родителю, home-каталогу или корню и показывать ненавязчивое уведомление;
- не сохранять credentials вместе с путём и удалять историю вместе с профилем;
- добавить миграцию SQLite, unit-тесты восстановления и UI-тест перезапуска.

**Критерии приёмки:**

- после перезапуска доступные локальные панели открываются на последних путях;
- один SFTP-профиль не получает путь другого профиля;
- неудачная навигация не затирает последний рабочий путь;
- недоступный сохранённый путь не мешает подключению и приводит к предсказуемому fallback.

**Результат:**

- versioned-записи в существующей SQLite-таблице settings сохраняют локальные пути отдельно для
  панели и корня диска, а удалённые пути — по стабильному идентификатору профиля;
- первый листинг ждёт загрузки snapshot, поэтому стартовый каталог не затирает сохранённый;
  вкладки и панели восстанавливаются после перезапуска, выбор диска открывает его последний путь;
- SFTP начинает с последнего успешного пути; при not-found/access-denied перебираются родители,
  начальный каталог и корень с ненавязчивым уведомлением, неудачный явный переход не сохраняется;
- удаление профиля очищает его историю, credentials с путями не сохраняются;
- сохранение путей можно отключить в настройках; по умолчанию оно включено, а отключение
  очищает локальную и удалённую историю;
- проверки: `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:integration`, `pnpm test:e2e`.

#### [x] T28. Запрашивать отсутствующий или неверный пароль подключения

**Зависимости:** T29.

**Цель:** позволить подключиться без сохранённого пароля и исправить ошибочный пароль без
редактирования всего профиля.

**Работы:**

- отличать authentication failure от сетевой, host-key и protocol ошибки;
- показывать парольный диалог, когда профиль использует password authentication, но секрет
  отсутствует;
- после отказа аутентификации показывать тот же диалог с возможностью повторного ввода;
- добавить действия «Подключиться», «Отмена» и флаг «Сохранить пароль»;
- до подтверждения сохранения держать введённый пароль только в памяти main process и очищать
  его после завершения попытки;
- при сохранении заменять credential через `safeStorage`, не записывая неверное значение заранее;
- не возвращать сохранённый пароль в renderer и не помещать его в ошибки или диагностику;
- не предлагать password fallback после ошибки ключа, если сервер его не поддерживает;
- ограничить автоматические повторы и оставить отмену доступной на каждом шаге;
- добавить integration-тесты отсутствующего, неверного, исправленного и отменённого пароля.

**Критерии приёмки:**

- профиль без сохранённого пароля подключается после ввода пароля в диалоге;
- неверный пароль можно исправить без закрытия подключения и редактирования профиля;
- пароль сохраняется только при явном выборе пользователя и только в защищённом хранилище;
- другие виды ошибок не маскируются парольным диалогом.

**Результат:**

- password-профиль разрешено создать без секрета; отсутствующий или отклонённый сервером пароль
  открывает отдельный диалог с повторным вводом, отменой и явным флагом сохранения;
- введённое значение очищается из формы, временно живёт только в main process и удаляется после
  попытки или отмены; credential заменяется через safeStorage только после успешного соединения;
- authentication, host-key, network и protocol failures имеют разные безопасные коды; парольный
  fallback не показывается для agent/private-key и других классов ошибок;
- Electron-сценарий проверяет неверный пароль, исправление, защищённое сохранение и повторное
  подключение без редактирования профиля;
- проверки: `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:integration`, `pnpm test:e2e`.

#### [x] T29. Показывать прогресс и статус SFTP-подключения

**Зависимости:** T07, T15.

- отмена прерывает ожидающее получение credentials и уничтожает клиент/socket, а закрытие канала

### Рекомендуемый порядок выполнения

Задачи не привязаны к датам. Порядок учитывает переиспользование общей инфраструктуры:

```text
Первый приоритет: T22, T23, T25

T24 + T25 → T26
T29 → T28
T16 → T27

T24 + T27 + T28 + T29 → T30
```

В первую очередь выполняются T22, T23 и T25. Они опираются только на уже реализованную
инфраструктуру и не зависят друг от друга. После них выполняются остальные задачи с учётом
указанных зависимостей. T30 выполняется последней, чтобы FTP сразу получил уже готовое
поведение конфликтов, credentials, статусов и последних путей, а не создавал отдельные
временные реализации этих сценариев.
