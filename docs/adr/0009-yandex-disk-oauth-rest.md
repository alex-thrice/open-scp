# ADR 0009: Яндекс Диск через REST API и OAuth PKCE

- Статус: реализовано; публичный Client ID предоставлен, реальная приёмка ожидается.
- Дата: 2026-10-19.

## Контекст

Владелец выбрал REST/OAuth с однократной регистрацией OpenSCP и 2026-10-19 предоставил
публичный Client ID для локальной/CI-конфигурации вне исходников. Callback и три scope подтверждены
публичными настройками Яндекса; настоящий вход ещё не проверен.
Документация Яндекса прямо разрешает обмен кода без client secret при передаче PKCE verifier:
https://yandex.ru/dev/id/doc/ru/codes/code-url.
WebDAV с паролем приложения рассматривался, но не выбран: он требует тарифа Яндекс 360
и имеет другую семантику удаления. T32 сохраняет REST API и основу OAuth для T33.

## Решение

- Добавить профили/пути `yandex`; путь — абсолютная строка относительно `disk:/`.
  Профиль хранит начальный каталог, timeout, ID/имя связанного аккаунта и ссылку на секрет
  OAuth. Импорт/экспорт не содержат токенов; дублирование OAuth-профиля требует нового входа.
- Авторизация выполняется в системном браузере. Общий main-сервис использует случайные
  `state`, verifier и S256 challenge, IPv4 loopback callback и одноразовое принятие кода.
  Каждый вход привязан к своему профилю; timeout/отмена не завершают чужую авторизацию.
  Посторонние callback и повторные параметры отклоняются. Ответ браузеру не содержит токенов.
- Зарегистрированный callback: `http://127.0.0.1:53682/oauth/yandex/callback`.
  Client ID задаётся через `OPENSCP_YANDEX_CLIENT_ID`: локально в игнорируемом `.env.local`,
  в GitHub Actions — через repository variable. Значение не хранится в исходниках/документации;
  без настройки вход отключён. ID включается в main bundle при сборке; client secret
  не принимается и не включается в пакет. Права: `cloud_api:disk.read`, `cloud_api:disk.write`,
  `cloud_api:disk.info`. Эти права и callback подтверждены публичными настройками приложения;
  выдача токена остаётся на ручную проверку.
- Token bundle хранится через CredentialService/safeStorage. Refresh выполняется однократно
  для конкурирующих запросов одного профиля, с client ID и refresh token без client secret.
  Отказ публичному refresh приводит к повторному входу, а не к встраиванию секретного ключа.
  Другой аккаунт нельзя незаметно подменить в уже связанном профиле.
- IPC содержит save/authorize/cancel/forget и безопасные состояния входа без credentials.
  Выход из OpenSCP удаляет локальные токены; отзыв разрешения на стороне Яндекса выполняется
  в настройках Яндекс ID и отдельно описывается в руководстве.
- API-клиент использует фиксированный HTTPS origin `https://cloud-api.yandex.net/v1/disk`.
  Метаданные ограничены по размеру; страницы проверяются по offset/total и принадлежности
  каталогу. Асинхронные операции опрашиваются до подтверждённого завершения с пределом времени.
- Временные upload/download URL проверяются отдельно и никогда не получают OAuth-заголовок.
  Redirect ограничен известными HTTPS-хостами передачи и числом переходов; PUT не повторяется
  автоматически. GET допускает ограниченный backoff/Retry-After с отменой.
- Потоки имеют ограниченные буферы. Очередь пишет временное имя и публикует через MOVE
  с явной политикой overwrite, без предварительного удаления назначения. Неопределённый
  результат публикации требует проверки. Resume, POSIX permissions, атомарность rename,
  checksum и server-side copy в первой версии не объявляются.
- Для fixtures разрешено явное внедрение main-конфигурации на loopback. Development Electron
  требует отдельного тестового флага; packaged-приложение игнорирует fixture endpoints.

## Последствия

Client ID поступает в development/release-сборку из внешней конфигурации; callback и права проверены.
Настоящий вход и refresh остаются на проверку. T32 остаётся открытой до реального smoke. Сохранённые профили старых типов и
таблицы SQLite не меняются; расширяются discriminated unions и безопасный IPC snapshot.
