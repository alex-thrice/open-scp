# Исследование скорости загрузки SFTP

Дата: 2026-09-18.

Пользователь сравнил один файл размером около 200 МБ на одном сервере:
WinSCP — около 16 Мбит/с, OpenSCP — около 500 кбит/с. Отношение — примерно 32.
Единицы приведены со слов пользователя; независимо от интерпретации бит/байт
отношение скоростей остаётся тем же.

## Подтверждённое ограничение OpenSCP

`src/main/providers/local/local-provider.ts` читает по 64 КиБ.
`src/main/transfers/transfer-engine.ts:683` ожидает `writer.write` перед следующим
блоком. `src/main/providers/sftp/sftp-provider.ts:353` внутри `openWrite` ожидает
ответ на каждый `sftp.write`. Таким образом, загрузка одного файла держит только
один неподтверждённый запрос записи.

Лимит `activeRequests >= 8` в SFTP-провайдере ограничивает число одновременно
выполняемых вызовов, но сам по себе не создаёт их: последовательный цикл использует
только один слот. Изменение числа 8 на 64 само по себе проблему не решает.
Увеличение `highWaterMark` также не создаёт параллельных SFTP-записей, пока callback
`write` и вызывающий код ждут подтверждения каждого блока.

При блоке 64 КиБ верхняя оценка скорости последовательной загрузки:

`скорость <= 65536 / время до подтверждения одного WRITE`.

| Время до ответа | Верхняя оценка | 200 МиБ, только ожидание ответов |
| --------------- | -------------- | -------------------------------- |
| 10 мс           | 6,25 МиБ/с     | 32 с                             |
| 20 мс           | 3,13 МиБ/с     | 64 с                             |
| 50 мс           | 1,25 МиБ/с     | 160 с                            |
| 100 мс          | 0,63 МиБ/с     | 320 с                            |

Это расчётные примеры, не измерение задержки сервера пользователя. Время ответа
включает сеть, обработку сервером и планирование исполнения.

## Как устроен WinSCP

В локальной копии исходников `C:/GitHub/winscp-master`:

- `source/core/SessionData.cpp:299`: `SFTPUploadQueue = 64` по умолчанию.
- `source/core/SftpFileSystem.cpp:1514`: `TSFTPUploadQueue` наследует асинхронную очередь.
- `source/core/SftpFileSystem.cpp:1674`: отправка ждёт освобождения места при достижении
  лимита очереди, вместо ожидания ответа после каждого блока.
- `source/core/SftpFileSystem.cpp:2243`: размер блока подбирается с учётом скорости,
  ограничений пакета и лимита скорости.

За счёт нескольких запросов в одном SSH-соединении WinSCP продолжает передавать
данные, пока сервер подтверждает предыдущие блоки. Для этого не требуется создавать
несколько соединений или загружать несколько файлов одновременно.
Этот механизм также описан в [официальной документации WinSCP](https://winscp.net/eng/docs/faq_slow#network_delaylatency).

Наша библиотека уже поддерживает такую передачу: `ssh2.fastPut` по умолчанию
использует 64 параллельных операции с блоком 32 КиБ. См.
[SFTP API ssh2](https://github.com/mscdex/ssh2/blob/v1.17.0/SFTP.md).
Менять библиотеку только ради очереди запросов не требуется.

## Воспроизводимый стенд

Добавлен `scripts/benchmark-sftp-upload.mjs`. Запуск из корня проекта на Node 24:

```sh
node scripts/benchmark-sftp-upload.mjs 200 10
node scripts/benchmark-sftp-upload.mjs 200 0
```

Первый аргумент — размер файла в МиБ, второй — задержка отправки сервером
подтверждения `WRITE` в миллисекундах. Фактическая задержка может быть больше из-за
точности таймеров ОС. Это имитация ожидания SFTP-ответов, а не эмуляция всей сети.

Стенд поднимает SSH/SFTP только на `127.0.0.1`, генерирует отдельный ключ сервера и
проверяет его fingerprint. Используется один и тот же случайный файл, соединение,
шифр AES-128-GCM, блок 64 КиБ и принимающая сторона в памяти. Сжатие отключено.
Идентификатор тестового сервера содержит OpenSSH, чтобы ssh2 допускал блок 64 КиБ
без дополнительного дробления. Это встроенный сервер ssh2, не настоящий OpenSSH.

Режим `provider` использует настоящие `LocalProvider`, `SftpConnection`,
`SftpProvider` и тот же последовательный цикл, что TransferEngine. Режимы
`fastPut-1`, `fastPut-8`, `fastPut-64` отличаются числом параллельных запросов
штатного `fastPut`. Время включает передачу и закрытие файла, но не подключение,
генерацию данных или последующую проверку SHA-256. После каждого режима проверяются
объём, отсутствие ожидающих ответов и SHA-256 всего принятого файла.

Результаты этого стенда нельзя выдавать за скорость реального сервера или запуск
самого WinSCP: он изолирует влияние очереди в нашей библиотеке.

### Измеренные результаты

Windows, Node 24.19.0, ssh2 1.17.0, native SSH binding отсутствует. Один прогон
каждого режима, 200 МиБ, одинаковый блок 64 КиБ; SHA-256 совпал во всех случаях.

| Режим                      | Задержка подтверждения задана 10 мс: время / скорость | Без добавленной задержки: время / скорость |
| -------------------------- | ----------------------------------------------------- | ------------------------------------------ |
| Текущие провайдеры OpenSCP | 49,924 с / 4,01 МиБ/с                                 | 3,711 с / 53,89 МиБ/с                      |
| `fastPut`, очередь 1       | 49,894 с / 4,01 МиБ/с                                 | 3,616 с / 55,31 МиБ/с                      |
| `fastPut`, очередь 8       | 6,893 с / 29,01 МиБ/с                                 | 3,260 с / 61,34 МиБ/с                      |
| `fastPut`, очередь 64      | 2,772 с / 72,15 МиБ/с                                 | 2,623 с / 76,25 МиБ/с                      |

В прогоне с задержкой сервер наблюдал максимум 1, 1, 8 и 32 ещё не подтверждённых
запроса соответственно. Настройка 64 — верхний предел, фактическое заполнение
зависит также от SSH-окна и скорости обработки. Таймер, запрошенный на 10 мс,
на этой ОС вместе с обработкой дал средний цикл последовательной записи около
15,6 мс; поэтому результат не равен расчётным 32 секундам из таблицы выше.

Очередь 64 ускорила передачу относительно текущего кода в **18 раз** при неизменной
библиотеке и шифре. Без добавленной задержки разница составляет около 1,4 раза.
Это подтверждает влияние ожидания ответов, но не определяет точный вклад остальных
факторов на сервере пользователя.

## Дополнительные наблюдения

- `pnpm-workspace.yaml` отключает сборку необязательного native-модуля ssh2 и
  исключает `cpu-features`. Это может влиять на предельную скорость, но не доказывает
  причину наблюдаемого падения. AES в ssh2 всё равно использует `node:crypto`;
  утверждение, что всё шифрование выполняется чистым JavaScript, неверно.
- Прогресс обновляется в памяти, SQLite не записывается после каждого блока.
- Общая очередь TransferEngine выполняет одну операцию за раз, но это не объясняет
  низкую скорость единственного большого файла при наличии очереди SFTP-запросов.
- Чтение SFTP тоже последовательное (`openRead`); скачивание имеет аналогичное
  ограничение. Проверка префикса при продолжении загрузки может дополнительно
  замедляться из-за этого. Для новой загрузки проверка префикса не нужна.
- Для серверов, не распознанных ssh2 как OpenSSH/dropbear, исходный предел записи
  составляет `34000 - 2048 = 31952` байта, если сервер не согласовал другие лимиты.
  Тогда один блок приложения 64 КиБ дробится библиотекой на три последовательных
  запроса. Увеличение только размера блока приложения не устраняет ожидания.

## Направление исправления

Нужна ограниченная очередь неподтверждённых SFTP-записей с отдельными смещениями,
ограничением памяти и backpressure. Отправка следующего блока должна идти до
подтверждения предыдущего, пока в очереди есть место. Управляющие запросы не должны
зависеть от заполненности очереди данных.

Закрытие файла и публикация временного `.openscp-part-…` обязаны ждать всех ответов
и проверять ошибки. При отмене и сбое нельзя закрывать handle раньше уже отправленных
операций или считать буферизованные байты подтверждёнными. Resume должен по-прежнему
проверять фактически записанный префикс. Простой вызов `fastPut` в обход этих контрактов
не является готовым исправлением.

Этот документ фиксирует первоначальное исследование до исправления. Очередь затем
реализована с настройками 64/32; итоги внедрения и сравнение SFTP, FTP и S3 приведены
в [отчёте о больших файлах](large-file-transfer-performance.md). Скрипт SFTP-стенда
теперь сравнивает текущий провайдер с очередями 1 и 64 и `fastPut` с очередью 64.
Для точной оценки ускорения у пользователя нужен повторный замер на том же сервере;
его задержка, диски и согласованные параметры SSH здесь не измерялись.
