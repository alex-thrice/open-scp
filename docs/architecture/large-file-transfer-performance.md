# Передача больших файлов: SFTP, FTP и S3

Дата: 2026-09-18.

## Изменения SFTP

Добавлена очередь неподтверждённых запросов одного файла внутри одного SSH-соединения.
По умолчанию отправляются до 64 блоков при загрузке и до 32 при скачивании — значения
`SFTPUploadQueue` и `SFTPDownloadQueue` из исходников WinSCP. Блок приложения остаётся
64 КиБ; это не полное воспроизведение адаптивного выбора размера пакетов WinSCP.

«Настройки → Передачи» содержит два числовых поля (1–128), сохранение и сброс к значениям
WinSCP. Настройки сохраняются между запусками, действуют на все SFTP-соединения при
начале следующего файла. Значение 1 предназначено для последовательных запросов.
Открытые потоки сохраняют выбранные при их создании параметры.

Очередь данных отделена от лимита восьми управляющих запросов. Память ограничена
числом блоков: полезные данные очереди загрузки по умолчанию занимают до 4 МиБ,
скачивания — около 2 МиБ, дополнительно существуют буферы потоков и SSH.
Прогресс загрузки изменяется после подтверждений. Ошибка и отмена дожидаются отправленных
запросов перед закрытием handle; `close` проверяет все подтверждения перед публикацией
временного файла. Продолжение по-прежнему проверяет SHA-256 записанного префикса.

Скачивание восстанавливает порядок ответов и дочитывает короткие блоки. Неожиданный
EOF внутри размера, полученного через stat, завершает передачу ошибкой.

Отдельный стенд с искусственной задержкой подтверждений WRITE 10 мс дал для 200 МиБ:
очередь 1 — **50,017 с**, очередь 64 в новом провайдере — **3,640 с**. Ускорение
реальной реализации составляет **13,7 раза** на этом стенде, SHA-256 совпал.
Для сравнения `fastPut` с очередью 64 дал 2,797 с. Задержка таймера ОС фактически
больше заданных 10 мс; это проверка механизма ожидания, не эмуляция всей сети.

## Сравнение с установленным WinSCP

Один случайный файл 200 МиБ, один компьютер, локальные контейнеры OpenSSH, vsftpd 3.0.5
и MinIO. OpenSCP запускает настоящие провайдеры через TransferEngine на Node 24.19.0;
WinSCP 6.5.6.0 — через установленную .NET assembly. Подключение, создание тестового файла
и SHA-256 исключены из времени; операции загрузки/скачивания, завершение и сопутствующие
операции с файлом включены. Для обоих клиентов проверен SHA-256 скачанного файла.

| Протокол | OpenSCP загрузка       | WinSCP загрузка        | OpenSCP скачивание     | WinSCP скачивание      |
| -------- | ---------------------- | ---------------------- | ---------------------- | ---------------------- |
| SFTP     | 3,494 с / 57,24 МиБ/с  | 2,495 с / 80,15 МиБ/с  | 2,734 с / 73,16 МиБ/с  | 3,291 с / 60,77 МиБ/с  |
| FTP      | 1,140 с / 175,39 МиБ/с | 1,628 с / 122,87 МиБ/с | 1,234 с / 162,14 МиБ/с | 1,651 с / 121,14 МиБ/с |
| S3       | 1,486 с / 134,58 МиБ/с | 3,223 с / 62,05 МиБ/с  | 1,368 с / 146,16 МиБ/с | 1,659 с / 120,54 МиБ/с |

Это один прогон каждого режима через loopback, с файловыми кэшами и локальными дисками.
OpenSCP выполнялся первым для каждого протокола. Эти данные подтверждают передачу больших
файлов и отсутствие прежнего кратного отставания, но не являются рейтингом клиентов и
не прогнозируют скорость WAN, AWS или другого SFTP-сервера. Шифры SFTP не принудительно
выравнивались между клиентами. FTP использовал незашифрованный локальный стенд, S3 — HTTP
к локальному MinIO. HTTPS/FTPS этим замером не покрыты.

## FTP

В `src/main/providers/ftp/ftp-provider.ts` используется `basic-ftp.uploadFrom`/
`downloadTo`, `PassThrough` и backpressure. Callback записи означает продвижение данных
по локальному потоку, а не ожидание отдельного FTP-подтверждения на каждый блок 64 КиБ.
Передача идёт непрерывно по TCP-соединению данных; финальный ответ сервера ожидается
при завершении. Аналога обнаруженного последовательного SFTP-WRITE здесь нет.

В WinSCP `source/core/FtpFileSystem.cpp` делегирует передачу FileZilla engine,
который также использует поток данных. Лимит параллельных SFTP-запросов к FTP неприменим.
На стенде больших файлов провала скорости не обнаружено, производственный FTP-код
не менялся.

WinSCP для контейнерного vsftpd требует `FtpForcePasvIp2=on`: сервер в PASV возвращает
внутренний адрес Docker. Настройка используется только тестовым сеансом; исходный
basic-ftp использует адрес управляющего соединения. Конфигурация пользователя не меняется.

## S3

`src/main/providers/s3/s3-upload.ts` уже использует multipart: базовая часть 8 МиБ,
до двух частей одновременно, ограничение памяти и ожидание частей перед Complete.
Размер части увеличивается при необходимости уложиться в 10 000 частей; текущая
реализация ограничивает его 64 МиБ. MD5, проверки размера, условная публикация и
журнал незавершённых multipart-загрузок сохраняются.

В локальных исходниках WinSCP (`source/core/S3FileSystem.cpp:2505`) размер части для
обычных файлов начинается с 5 МиБ, а `S3_upload_part` вызывается в последовательном
цикле частей. Нельзя механически переносить сюда SFTP-очередь 64: S3 оперирует частями
на несколько мегабайт и отдельными HTTP-запросами. Скачивание S3 в обоих случаях
представляет поток ответа GET. На стенде OpenSCP не уступил WinSCP; оснований менять
две части на 64 или расширять настройки S3 по этому замеру нет.

## Воспроизведение

Из корня проекта на Node 24, с Docker и установленным WinSCP в стандартной папке:

```sh
node tests/fixtures/environment.mjs up
node scripts/benchmark-protocol-transfers.mjs 200
node scripts/benchmark-sftp-upload.mjs 200 10
```

Для отдельного протокола: `node scripts/benchmark-protocol-transfers.mjs 200 s3`.
Для проверки только OpenSCP без Windows/WinSCP добавьте `skip-winscp`:
`node scripts/benchmark-protocol-transfers.mjs 200 s3 skip-winscp`.
Скрипты используют только тестовые учётные записи и loopback, создают уникальные имена
и удаляют собственные файлы после успешных проверок. Необходимые для диагностики логи
и JSON-результаты записываются в игнорируемый `test-results`.

## Повторная проверка SFTP и облачных подключений, 2026-10-19

Коммит ускорения SFTP `3a56ff9` входит в текущую ветку. С тех пор код SFTP-провайдера,
очередей чтения/записи и значения настроек 64/32 не изменялись. Фабрика провайдера
по-прежнему читает сохранённые настройки при открытии потока. Изменение диалогов
сохраняет эти настройки по подтверждению, отмена оставляет прежние значения.

Повторный запуск `node scripts/benchmark-sftp-upload.mjs 200 10` на Node 24.19.0:

| Режим                    | Время    | Скорость    |
| ------------------------ | -------- | ----------- |
| Провайдер, очередь 1     | 49,602 с | 4,03 МиБ/с  |
| Провайдер, очередь 64    | 3,812 с  | 52,46 МиБ/с |
| ssh2 fastPut, очередь 64 | 2,919 с  | 68,51 МиБ/с |

SHA-256 совпал во всех режимах. Ускорение текущего провайдера относительно очереди 1
составляет 13 раз. Это проверка механизма на локальном SSH/SFTP-стенде с задержкой
подтверждения WRITE 10 мс; скорость конкретного удалённого сервера здесь не измерялась.

### Google Drive

В resumable-загрузке был блок 1 МиБ с ожиданием ответа после каждого запроса.
Кроме сетевого ожидания, сборка блока из чтений по 64 КиБ каждый раз копировала
накопленный буфер через `Buffer.concat`. Блок увеличен до 8 МиБ, сборка использует
один буфер размером не больше 8 МиБ и копирует каждый входящий байт один раз.
При частичном подтверждении сохраняется неподтверждённый остаток.

Размер кратен 256 КиБ, как требует [протокол Google Drive](https://developers.google.com/workspace/drive/api/guides/manage-uploads#http---multiple-requests).
Документация рекомендует увеличивать блок для эффективности. Одновременная отправка
перекрывающихся диапазонов одной resumable-сессии не добавлялась: следующий запрос
использует подтверждённое сервером смещение. Последний блок, включая ровно 8 МиБ,
отправляется только после проверки источника и назначения при закрытии потока.
Прогресс по-прежнему учитывает подтверждённые байты.

Воспроизведение: `node scripts/benchmark-google-upload.mjs 64 40`.
Скрипт использует настоящие LocalProvider, TransferEngine и GoogleProvider,
локальный API-стенд и отдельный временный файл. Авторизация также тестовая.
Время включает общую очередь, HTTP-запросы и завершение; SHA-256 проверяется после замера.

| Реализация                  | Запросы с данными | Время   | Скорость    |
| --------------------------- | ----------------- | ------- | ----------- |
| Блок 1 МиБ, до изменения    | 64                | 3,990 с | 16,04 МиБ/с |
| Блок 8 МиБ, после изменения | 8                 | 0,723 с | 88,52 МиБ/с |

Размер файла 64 МиБ, искусственная задержка ответа на блок 40 мс, SHA-256 совпал.
Это по одному прогону на loopback с приёмником в памяти, включая издержки тестового API,
а не результат загрузки в настоящий Google Drive и не обещание ускорения в 5,5 раза
на любом подключении. За пределами собственного буфера остаются буферы HTTP/TLS и источника.

### Яндекс Диск и Mail.ru Cloud

В текущем коде оба провайдера отправляют файл одним HTTP PUT с потоковым телом,
ограничением буферов и повторным использованием соединений. Ожидание callback
`request.write` относится к локальной отправке данных в сокет, а не к отдельному
HTTP-ответу облака на каждый блок 64 КиБ. Причины прежнего провала SFTP здесь нет.

Общая очередь TransferEngine выполняет задания и файлы каталога последовательно.
Для большого числа мелких файлов перспективно ограниченное параллельное выполнение
независимых передач, чтобы перекрывать запросы метаданных и создание файлов.
Это отдельное изменение планировщика с проверками конфликтов, отмены и повторов;
в этой проверке оно не вводилось. Оснований обещать ускорение одного большого файла
Яндекса или Mail.ru только от увеличения буфера пока нет: нужен замер реального
соединения с учётом сети и ограничений сервиса.
