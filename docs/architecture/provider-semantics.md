# Семантика провайдеров файловой системы

## Назначение общего контракта

`FileSystemProvider` даёт UI и Transfer Engine единый lifecycle, list/stat, создание каталогов,
удаление, rename и потоковый ввод-вывод. Контракт не утверждает, что все провайдеры имеют
одинаковую файловую семантику. Доступность команды определяется `ProviderCapabilities`, а путь
остаётся discriminated union с вариантом для конкретного провайдера.

Provider implementation и протокольные библиотеки находятся только в main process. Renderer,
preload и shared не импортируют AWS SDK, `basic-ftp`, ssh2, SQLite и Node.js filesystem API.

## Пути

- **Local:** абсолютный системный путь. Нормализацию выполняет Node.js для текущей платформы;
  экземпляр `LocalProvider` ограничивает операции настроенным root и отклоняет выход за него.
- **SFTP:** отдельная строка удалённого пути. Даже если сервер обычно использует POSIX-подобный
  синтаксис, локальные `path.resolve` и разделители к нему не применяются.
- **FTP:** отдельная абсолютная строка удалённого пути с POSIX-разделителем. Управляющие символы,
  способные добавить FTP-команду, отклоняются до обращения к protocol library.
- **S3:** пара `bucket` + `key`. Key не является POSIX-путём: символ `/` используется соглашением
  о prefix, но не создаёт настоящий каталог.

Пути разных provider kinds нельзя передавать одному экземпляру провайдера или смешивать в
rename. Кросс-провайдерная передача выполняется Transfer Engine через потоки.

## Сравнение семантики

| Свойство           | Local                                                       | SFTP                                       | FTP                                  | S3                                                       |
| ------------------ | ----------------------------------------------------------- | ------------------------------------------ | ------------------------------------ | -------------------------------------------------------- |
| Настоящие каталоги | Да                                                          | Да                                         | Да                                   | Нет, только prefixes и optional marker objects           |
| Права доступа      | POSIX mode там, где поддерживает ОС                         | Серверные mode/ACL                         | Не объявляются                       | Не файловые permissions; отдельная IAM/ACL модель        |
| Симлинки           | Отображаются явно; безопасные операции не следуют им неявно | Возможны и зависят от сервера              | Не объявляются                       | Нет                                                      |
| Rename             | Атомарен внутри одной файловой системы                      | Capability зависит от сервера и расширений | Поддержан, но атомарность не обещана | Нет; моделируется copy + delete                          |
| Server-side copy   | Не входит в базовый LocalProvider                           | Обычно нет                                 | Нет                                  | Возможен                                                 |
| Multipart upload   | Нет                                                         | Нет                                        | Нет                                  | Возможен                                                 |
| Resume             | Должен объявляться отдельно для read и write                | Зависит от server/file mode                | Не объявляется в первой версии       | Зависит от multipart/range semantics                     |
| Checksum           | Не обещан базовым контрактом                                | Зависит от расширений                      | Не объявляется                       | Зависит от API и не равен multipart ETag во всех случаях |

FTP v1 поддерживает только passive mode и обычный FTP без TLS. MLSD предпочтителен; fallback на
`LIST -a`/`LIST` сохраняет навигацию, но не выдаёт недостоверную дату изменения за точную.
Подробные границы и отклонённые варианты: `docs/adr/0006-ftp-v1.md`.

`atomicRename: false` не означает, что UI может молча заменить rename последовательностью copy +
delete. S3Provider реализует составную операцию в main process, UI предварительно предупреждает
о неатомарности; ошибка оставляет явный частичный результат, без скрытого удаления/rollback.
Transfer Engine для S3 upload использует условную multipart-финализацию, а не эмулирует rename.
Подробные условия и совместимые расширения контрактов: `s3.md`.

## Lifecycle и ошибки

Состояния соединения: `disconnected → connecting → connected → disconnecting → disconnected`.
Ошибка подключения переводит провайдер в `failed`; повторное подключение является явной
операцией.

Публичные операции возвращают `ProviderError` с нормализованным машинным кодом и ключом
локализации. `protocolCause` сохраняет provider kind, операцию и нативный/протокольный код, а
исходная ошибка остаётся в `cause` main process. Raw message, stack trace, системный путь и
значения payload не должны сериализоваться в renderer.

## Потоки и отмена

`openRead` и `openWrite` используют Web Streams, чтобы общий контракт не зависел от Node.js
stream types. Провайдер обрабатывает данные ограниченными чанками и проверяет `AbortSignal` до и
между длительными шагами. Отмена возвращается как `PROVIDER_CANCELLED`.

Рекурсивное удаление LocalProvider использует `lstat`: каталог-симлинк удаляется как ссылка, а
его target не обходится. Промежуточные симлинки в пути отклоняются, чтобы операция не покинула
настроенный root.
